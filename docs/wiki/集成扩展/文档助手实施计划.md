# 文档助手（doc-assistant）实施计划

> 基于 [《文档助手设计》](./文档助手设计.md) · 目标：交付可运行、可验收的前后端功能

## 0. 总览

| 项 | 说明 |
|----|------|
| 目标 | 实现「文档助手」独立模块：模板管理（个人私有）、异步生成、历史记录、单章续写/版本化、Word 导出 |
| 范围 | 后端（模板 CRUD + 生成编排 + 3 张表 + 异步任务 + 导出）+ 前端（入口 + 4 页面 + i18n） |
| 验收顺序 | 后端模板 CRUD → 后端异步生成 → 后端导出/版本 → 前端页面 → 端到端验收 |
| 任务类型 | `doc-assistant:generate`（`TypeDocumentGenerate`），Lite + 标准双模式注册 |

## 1. 实施阶段与任务清单

### 阶段 1：后端地基（模板 CRUD + 数据表）

**1.1** 新增三张表 repo + 建表迁移
- `internal/repository/doc_template_repo.go`（`doc_templates`）
- `internal/repository/doc_generation_task_repo.go`（`doc_generation_tasks`）
- `internal/repository/doc_document_repo.go`（`doc_documents`）
- SQL 迁移文件参照现有迁移目录组织（`internal/repository/*.sql` 或 versioned 迁移），表结构见设计第 8 章。
- **验收点**：迁移本地（`.env.local` PostgreSQL 127.0.0.1:5434）可执行，`\d` 可见三张表。

**1.2** 模板 service + handler
- `internal/application/service/doc_assistant/template_service.go`：CRUD + 章节骨架校验（空 chapters 拒绝、章节数≤30 夹紧、max_words 夹紧 [200,5000]）+ owner 隔离 + 删除软删。
- `internal/handler/doc_assistant.go`：`GET/POST /api/v1/doc-assistant/templates`、`GET/PUT/DELETE /api/v1/doc-assistant/templates/:id`。
- `internal/router/router.go` 注册路由组；`internal/container/container.go` 注入依赖。
- **验收点**：curl 建/改/删/查模板，校验规则生效，他人 tenant 读不到。

### 阶段 2：后端异步生成

**2.1** 新增任务类型注册
- `internal/types/task.go`：加 `TypeDocumentGenerate = "doc-assistant:generate"`，加入第 76 行校验列表。
- `internal/router/task.go`（标准 asynq）`mux.HandleFunc(types.TypeDocumentGenerate, ...)`。
- `internal/router/sync_task.go`（Lite）`RegisterSyncHandlers` 注册同 handler。
- `internal/router/task_inspector.go` 已知任务类型表加入该类型。
- **验收点**：双模式注册后 `go build` 通过，既有任务分发测试不破。

**2.2** 生成编排 service
- `internal/application/service/doc_assistant/generate_service.go`：
  - 任务创建（写 `doc_generation_tasks`，status=pending，存 template_snapshot + kb_ids + kb_filters + model_id + theme + extra_requirement）。
  - 任务 handler（幂等 checkpoint 续跑）：逐章 → 检索（knowledge-search service，kb_ids + kb_filters + query=主题+补充+章节指令）→ 素材不足判定（must_reference 开关）→ `GetChatModel + chat.Chat` 生成该章 → 引用归并 references → 章节落库 checkpoint。
  - 收尾：success / partial_success / failed；md 文件落 `.local-data`。
- **验收点**（复用本机 Ollama embedding + chat 模型，参照 project_memory 已跑通配置）：创建任务 → 状态流转 → 各章有 content + references；素材不足两种开关行为正确；单章失败 → partial_success + 该章可重生成。

**2.3** 版本化与单章续写
- `doc_documents` 落版本：首次生成 v1；`POST .../documents/:id/chapters/:no/regenerate` → v+1 仅替换该章；编辑保存文字 → 新版本（`edited` 标记）。
- 整篇「重新生成」→ 创建新任务。
- **验收点**：单章续写 version+1，其余章内容不变；旧版可回退查看。

### 阶段 3：后端导出

**3.1** `export_service.go`
- Markdown 文件写入（完成时）与读取（预览）。
- md→docx：goldmark 解析 → 标题映射 Word 标题样式、段落/列表输出；复杂元素降级为段落文本。
- 输出目录 `<data_path>/doc_assistant/<document_id>/v<version>/`，md 常驻、docx 按需生成。
- **验收点**：导出 .docx 可正常打开，标题为 Word 标题样式。

### 阶段 4：前端

**4.1** 导航 + API client
- 导航新增「文档助手」入口；`api/doc-assistant` client 封装。
- **4.2** 模板管理页：列表 + 编辑弹窗（章节骨架：增删章节/指令/篇幅/must_reference 开关）。
- **4.3** 生成文档页：选模板 → 选素材知识库（多选 + 可选过滤）→ 选模型 → 主题 + 补充要求 → 提交。
- **4.4** 历史列表页：任务状态 / 成功文档 / 失败重试 / 重新生成 / 删除。
- **4.5** 文档详情页：章节树 + 正文预览 + 单章编辑续写 + 导出 Markdown/Word + 版本切换。
- **4.6** i18n：zh-CN / en-US / ko-KR / ru-RU 新增 `docAssistant.*`。
- **验收点**：前端本地（`.run-frontend.ps1`，5173）可创建模板并触发生成，页面交互与后端连通。

### 阶段 5：端到端验收与人机核对

- 对照设计第 12 章 7 条验收标准逐条实测（复用本机 Ollama 模型库 nomic-embed-text + 一个 chat 模型）。
- 回归：`go test ./internal/application/service/... ./internal/handler/... ./internal/router/... ./internal/types/...`。
- 清理验收测试数据（模板 / 任务 / 文档 / 测试库，参照既往 topic_search 验收后的清理流程）。

## 2. 关键实现决策

1. **模型选择复用模型管理**：生成文档的对话模型 = 模型管理里 `KnowledgeQA`（前端 type=chat）类型的模型。用户生成时从该类型下拉选择，`doc_generation_tasks.model_id` 存模型 ID，后台 `GetChatModel(ctx, modelID)` 解析（`internal/application/service/model.go:591`）。与摘要/问题生成共用同一入口，不新增模型能力。**前提**：模型管理须已注册可用对话模型（本机 Ollama 需先注册一个 chat 模型，如 qwen2.5）。
2. **prompt 复用**：逐章生成组装参考 `knowledge_process.go` 的 `RenderPromptPlaceholders + WithLLMCallMetadata + chat.ChatOptions`，不新造模型调用层。
3. **Checkpoint 续跑**：每章完成即落库，任务重试从第一个未完成章节续跑，避免重复消耗 LLM 配额。
4. **Word 选型**：纯 Go（goldmark + 手写 docx XML），不引入 pandoc，契合 Lite 单文件分发。
5. **模板软删 + 快照**：模板删改不影响历史文档（引用 `template_snapshot`）。
6. **双模式任务**：`TypeDocumentGenerate` 必须同时注册到 `sync_task.go`（Lite）与 `task.go`（标准 asynq），缺一则某模式生成失败。

## 3. 风险与对策

| 风险 | 对策 |
|------|------|
| 逐章多轮 LLM 配额高、耗时长 | 每章 checkpoint + 只续跑失败章；max_words 夹紧上限 |
| 素材不足导致大量跳过 | must_reference 开关 + 全部 skipped 时任务 failed 明示 |
| docx 复杂元素丢失 | v1 明确降级为段落文本，列入已知局限，不承诺表格 |
| 双模式注册遗漏 | 2.1 步骤以"两处注册"为完成定义，回归测试覆盖 |
| 本机无 GPU/聊天模型 | 复用已跑通的 Ollama；无可用 chat 模型时用已有 LLM 配置，无法则明确告知用户需要先配置 |

## 4. 验收顺序（执行序）

1. 阶段 1（后端地基）→ 阶段 2（异步生成）→ 阶段 3（导出）每完成即 `go build` + 单测验证。
2. 阶段 4（前端）本地起服务实测页面。
3. 阶段 5：对照 7 条验收标准端到端核对，最后清理测试数据。

## 5. 交付物

- 后端：模板/任务/文档三表 + 模板 CRUD API + 生成编排 service + 双模式任务注册 + 导出 service。
- 前端：入口 + 4 页面 + i18n。
- 文档：本计划 + 设计文档；验收后按需更新。
